# Device connection and Diagnostics

This records the earlier connection-only phase. Live Data Logs now adds explicit maintenance, verified transfer and conditional deletion; see [Data Logs](DATA_LOGS.md) for current behavior and validation.

This feature extends the approved compact WPF shell with real serial observation. The source of truth remains `references/USB_PROTOCOL.md`, unchanged. There are no log, deletion, firmware, maintenance-entry, or test-control workflows.

## Implemented

- `src/CellQ.Protocol`: a WPF-independent byte-stream parser, CRC16-CCITT-FALSE, strict HELLO response parsing, transport interfaces, connection snapshots, and a single-owner asynchronous connection service.
- `src/CellQ.Desktop/Services`: a `System.IO.Ports` adapter configured before open with 250000 baud, 8-N-1, DTR/RTS disabled and no handshake; port enumeration does not open devices.
- Device selectors list only currently present ports whose Windows device name identifies an Arduino Mega 2560 (or the generic Arduino Mega name). Mega 1280, other boards, generic USB serial devices and unknown names are excluded at the user's request. Candidates are displayed only as `COM10`; a successful identification changes just that candidate to `CellQ (COM10)`. Disconnect, failure or an unconfirmed update state clears the CellQ label. Selection always holds the raw COM name, including for firmware/log workflows; no remembered COM number is proof of identity.
- Discovery reads the Windows Ports device setup class with `DIGCF_PRESENT`, obtains its friendly name (device description only when no friendly name is available) and reads `PortName` from its device registry key with query-only access. It uses the built-in [SetupAPI metadata functions](https://learn.microsoft.com/en-us/windows/win32/api/setupapi/nf-setupapi-setupdigetdeviceregistrypropertyw); there is no new package, VID/PID-only filter, serial probe or automatic connection. Missing/unmatched metadata never falls back to listing all ports. Matching ports are deduplicated and sorted numerically, and refresh preserves a still-present selection. A failed metadata query is reported; an empty match list has a plain-language USB connection hint.
- Device shows connection, firmware, readable device state and last check time. Serial settings and original errors are available in a collapsed Technical details section. Mode remains the last HELLO observation. No identity is invented before a valid response or retained after disconnection.
- Diagnostics uses the same reader and connection as Device. Readable activity is the default; Technical details shows original debug/protocol lines, framing faults and local events, with filtering, display pause, in-memory clear and copyable full selected text. Only receive time is assigned by the host; arbitrary debug payloads are not reinterpreted.
- Commands are serialized. The only transmitted application command is `CQ1,HELLO\n`, on explicit connect or Refresh status. Page navigation, switching normal/technical views, disconnect, cancellation, and shutdown send no commands. Existing MAINT is reported without changing it.
- Fragmented ASCII and binary inputs share one incremental parser. Binary type/length/CRC16 are validated; offset and payload bytes are preserved. Binary payloads cannot become fake debug or HELLO responses.
- Unexpected/malformed HELLO responses, read/write errors and identification timeouts close the port and clear stale state. Cancellation remains responsive. A close failure retains ownership until close succeeds, preventing a second port from being opened.
- SDK, direct serial dependency and transitive dependency graph are pinned. The fake-device transport is test-only.

## Host policy and limits

The protocol does not specify a numeric HELLO timeout. This feature uses a three-second response deadline; an uncertain result closes the port and requires an explicit reconnect. On initial Connect only, an exact `CQ1,ERR,SYNTAX` response permits one retry of the unchanged `CQ1,HELLO` command after a cancellable 250 ms wait. The first rejection must be fully received before another request is sent. The same port, baud rate and disabled DTR/RTS are retained; no reset, blank line or maintenance command is sent. Both attempts and the original rejection are retained in Diagnostics. A repeated rejection closes the connection without an identity; other replies, framing failures, timeouts and status/workflow refreshes are not retried by this policy. Responses received during the wait are unsolicited and cannot establish identity. The user confirmed that this recovery connects the second Windows 11 computer/Mega running v1.0.1. Its underlying hardware/driver cause remains unconfirmed.

Read timeout polling is 250 ms for cancellation, and write timeout is 1,000 ms. Silence between debug lines is not an error. The received ASCII line limit is 8,192 bytes as a defensive host buffer bound; the protocol's 79-byte limit applies to transmitted commands.

Diagnostics retains at most 2,000 visible and 2,000 queued messages. Display updates drain at most 200 queued entries every 100 ms. Older discarded entries are counted. Pausing display does not stop parsing or HELLO response processing. Clear view affects this local memory only.

No active GET exists in this feature. Valid binary frames are reported as unexpected transfer traffic; there is no file assembly, expected transfer offset, CRC32/whole-file verification, storage write or CANCEL command. Those belong to a later transfer workflow.

The preceding COM10 recovery update passed zero build warnings/errors, 1,414 core assertions across 116 cases and 216 WPF/packaging checks. Fourteen added simulator cases cover fragmented syntax rejection followed by valid identification in every reported mode, persistent rejection, other invalid replies, timeout after retry, token/Disconnect cancellation during the wait, unsolicited stale identity, and unchanged refresh failure handling. No physical port was opened during development; the user subsequently confirmed connection succeeds on the second Windows 11 computer/Mega running v1.0.1.

Final Release validation on 2026-10-09, including the subsequent plain-language UI: build succeeded with **zero warnings and errors**; **1,095 protocol assertions across 19 cases** and **91 WPF UI checks** passed. Tests opened no physical serial ports. The UI harness constructed an unopened real SerialPort object to verify adapter settings, then used an injected fake transport for all traffic.

The Release solution build and two executable test harnesses run with `build.ps1`. The protocol harness tests every two-part split, bytewise input, and deterministic random fragmentation of mixed D/CQ1/binary traffic; independent CRC test vector; boundary frame lengths and offsets; embedded newlines and command-looking payloads; corrupt/truncated input and resynchronization; exact HELLO modes; concurrent requests; timeouts; cancellation while opening/waiting; bad responses; disconnect/reconnect; EOF; access errors; and failed port close.

The WPF harness verifies one shared connection, actual serial factory settings without opening a port, empty initial Diagnostics, HELLO-derived fields, page navigation without transmission, raw/long debug display, filtering, paused-display reader operation, local-only clear, stale identity removal and shutdown. The simpler UI checks cover readable mode/action names, collapsed serial settings that remain accessible, normal activity filtering/search, switching technical views without losing original messages and clearing raw selection when hiding details. It also checks the existing shell navigation, sample pages, Device/Diagnostics minimum layout, raster scaling and absence of WPF binding warnings/errors.
